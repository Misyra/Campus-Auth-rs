## R 组：安全与信任边界（P1/P2，先做）

### R1. SSRF 防护补 IPv4-mapped IPv6 与保留段

**问题**（确认）：`src/web/ssrf.rs:37-44` V6 分支只查 loopback/unspecified/multicast/ULA/link-local，`::ffff:127.0.0.1`、`::ffff:169.254.169.254` 等 mapped 地址全部漏过，OS 按 IPv4 直连回环/链路本地；`:29-36` V4 分支缺 CGNAT `100.64.0.0/10` 与 `198.18.0.0/15`。

**方案**：
- V6 分支先 `v6.to_ipv4_mapped()` 解包，命中则按 V4 规则判定；
- V4 分支补 `100.64.0.0/10` 与 `198.18.0.0/15` 显式区间检查。

**验收**：新增单测：`::ffff:127.0.0.1`、`::ffff:169.254.169.254`、`100.64.1.1`、`198.18.0.5` 均 restricted；公网地址不受影响。fetch-url 相关路由测试回归。

### R2. API token 改常量时间比较

**问题**（确认，严重度下调至低）：`src/web/auth.rs:153` `token == expected` 为短路比较。服务仅绑 127.0.0.1，本机同用户进程威胁模型下无增量暴露面，但修复成本一行。

**方案**：XOR 累积式常量时间比较（不引子 crate，手写 ~5 行）。

### R3. MinGit 下载补 sha256 校验（严重度下调 P3，仍建议做）

**问题**（确认）：`src/environment/git.rs:57-66` MinGit zip 无任何完整性校验即解压执行；uv 有 `.sha256` 校验而 git 没有。

**方案**：复用现成 `updater::check::fetch_sha256_assoc` + `verify_sha256` 流程；校验失败不落盘。

### R4. 迁移 profile id 路径穿越

**问题**（确认）：`src/config/migration.rs:85` 用未校验的 v5 profile id 直接 join 进 profiles_dir 写盘（对比 service.rs:108-117 新增路径有严格校验）。前提是攻击者已能改写配置文件，属纵深防御。

**方案**：迁移写盘前过同一 `is_valid_profile_id`，非法 id slugify 或跳过并告警。

### R5. repo 代理响应体上限

**问题**（确认）：`src/web/routes/repo.rs:73` `resp.json()` 无体积上限，仅 15s 总超时封顶流量，大带宽源可在窗口内推入数百 MB 致内存膨胀。

**方案**：改 `bytes_stream()` 累积并在阈值（如 8MB）截断报错；或 `Content-Length` 预检 + 分块上限。

## F 组：并发与状态一致性（P2）

### F1. EnvironmentManager 引导互斥

**问题**（确认）：`src/environment/mod.rs:349-354` `bootstrap_capability` 无互斥；任务执行（tasks/executor.rs:110）、Web 安装浏览器（routes/system.rs:443）、OCR 安装（routes/ocr.rs:130）三处可并发跑 uv sync/playwright install 踩踏同一 .venv，write_status 交错覆盖。

**方案**：入口加 `tokio::sync::Mutex` 或 AtomicBool compare_exchange（仿 UpdaterService.update_in_progress）；已在进行中则返回「安装中」错误或等待完成。

### F2. Bridge 超时宽限误杀新会话

**问题**（确认）：`src/bridge/mod.rs:324-331` 超时宽限循环只查 `current_request_id.is_none()` 不校验归属：请求 A 超时后新请求 B 占用槽位时被误判"未自愈"，kill_worker_now 连坐 B。

**方案**：Cancel 时记录 `stuck_request_id`，宽限循环仅在 `current_request_id == stuck_request_id` 时判卡死强杀。

### F3. OCR 执行期间 idle timer 强杀 Worker

**问题**（确认）：`src/bridge/mod.rs:1048-1056` OCR 走轻量旁路不刷新 idle timer（默认 300s），第 299 秒开始的耗时 OCR 可在执行中途被 handle_idle_timeout 强杀，Python shutdown 排队超 5s 被 kill，pending drain 成 WorkerCrashed。

**方案**：handle_idle_timeout 增加 pending_requests/cancel_registry 非空检查；或 OCR 执行路径刷新 last_activity 并重置计时器。

### F4. Start/Resume 绕过暂停门控

**问题**（确认）：`src/engine/run_loop.rs:164-175, 271-273` 定时器分支有 `is_any_pause_active()` 门控，但 Start/Resume 的立即检测没有——暂停时段内手动 Start/Resume 会触发探测乃至自动登录。

**方案**：两处立即检测前加同一门控；暂停中则记日志跳过。

### F5. 引擎内联探测阻塞命令通道

**问题**（确认）：`run_loop.rs:226-262` TestNetwork 与周期检测在引擎单 task 内联 await probe，网络黑洞时 Start/Stop/**Shutdown** 排队数十秒；slot.test_network 的 30s oneshot 也可能因引擎忙误报超时。

**方案**：probe 移入 spawn 的后台任务，结果经 mpsc 回传主循环（与登录结果同模式），命令保持即时响应。

### F6. 抢占后 close_browser 与新会话竞争窗口

**问题**（确认）：`login/session.rs:637-692` set_result 先于 close_browser（≤8s）返回；`login/mod.rs:347` 抢占方 await_result 即创建新会话复用同一 Worker——旧的 close_browser 可能关掉新会话刚建的浏览器。

**方案**：抢占路径等待旧会话完全收尾（JoinHandle 或 close_browser 完成）再放行新会话；或将 close_browser 延迟到槽位确认无后继时执行。

### F7. 配置读-改-写持锁

**问题**（确认）：`src/config/profiles.rs:186-207` switch_profile/set_auto_switch 的 load-modify 序列在 settings_lock 外，save 整份覆盖写，并发提交丢失更新。

**方案**：提供持有锁的 `modify_settings(f)` 把读-改-写移入临界区，调用点迁移。

### F8. tmp 残留清理失配 → 幽灵 Profile

**问题**（确认）：`service.rs:202-208` 只删扩展名 `tmp` 的文件，实际临时名为 `.tmp_XXXX.json`（io.rs:29-31），且不扫 profiles_dir；崩溃残留永久累积并被 load_all_profiles 当 Profile 解析。

**方案**：按 `.tmp_` 前缀清理并覆盖 profiles_dir；load_all_profiles 跳过 `.tmp_` 前缀。

### F9. 后台待应用更新与手动更新无互斥

**问题**（确认）：`container.rs:174-190` apply_pending_on_startup 不持 update_in_progress 标记，2s 错峰只是缩小碰撞窗口，可双写 pending.json 并重复 spawn helper。

**方案**：两条路径统一走 UpdaterService 的 in-progress 标记（compare_exchange）。

### F10. 解密失败标志的副作用与作用域

**问题**（部分成立→按确认处理短板）：`crypto.rs:162-163` 任一密文解密成功即清全局 decryption_failed，A Profile 损坏提示被无关 B 抹掉；查询接口 can_decrypt_password 自带副作用（service.rs:410）。

**方案**：按 profile 记失败集合；查询接口只读不变更状态。

### F11. uv 半成品残留后永久 ready

**问题**（确认）：`bootstrap.rs:170-171` 就绪仅凭 environment/uv.exe 存在；`uv.rs:179-183` copy 回退半途失败残留部分写入的 uv_dest，此后永不重下且无法自愈。

**方案**：copy 回退改为 copy 到 tmp 再 rename；copy 失败清理半成品 uv_dest；本地 uv.exe 存在时也跑一次 `--version` 校验再置 ready。

### F12. 调度器时钟前跳与外部修改不感知

**问题**（确认，两条合并为一个任务卡）：
- `cron_loop.rs:68-77` sleep 目标一次性换算单调 Instant，时钟前跳漏触发；Linux 休眠唤醒补跑行为与 Windows 不一致；
- `cron_loop.rs:200-233` 无文件监听，运行期手工删除/修改任务 JSON 不被感知，幽灵任务持续触发。

**方案**：
- 长睡眠分片（单次 ≤60s），每次醒来用 SystemTime 重估目标（现有 fire_due_tasks 单次补偿逻辑已能去重）；
- cron_loop 加低频（5-10 分钟）无条件重扫兜底（引入 notify 可选，兜底扫描已覆盖主要场景）。

## A 组：高收益重构（ArchScout 结论）

> 总体判断：代码库已经历多轮系统化修复（M1/M5/C1-C3/A2/B3 标注遍布），以下嫌疑目标经查证**不应施工**：bridge/mod.rs 再拆分（单一 Mutex 临界区，拆分重造竞态）、engine/login/scheduler 三状态机统一抽象（本质不同，ServiceHandle 已是公共 seam）、scheduler↔tasks 合并（无重叠）、sha256 双形态合流、environment 重试 helper 化。真正值得做的 8 条：

### A-1. 抽出 src/logging.rs，删除「格式化再反解析」（最高性价比）
- 痛点：launcher.rs:376-703 内嵌 ~330 行日志子系统；broadcast 层格式化字符串后被 parse_log_line(L660-703) 三格式回退反解析——时间戳伪造（L662 chrono::now）、非标准行静默降级 INFO；system.rs:243 还有第二套 JSON 解析器；launcher 全文件零测试。
- 方案：新建 src/logging.rs 迁入全部日志设施；BroadcastWriter 改实现 tracing_subscriber Layer，on_event 直接从 metadata+字段 visitor 构造 LogEntry 发 broadcast，删除全部文本反解析。
- 收益：消除一类正确性缺陷；每条日志省一次序列化+解析；launcher 减重 ~30%。工作量 S-M。

### A-2. LoginSession 改依赖既有 BridgeApi trait，解锁核心状态机单测
- 痛点：session.rs:171/202 依赖具体 Arc<BridgeSupervisor>；BridgeApi（bridge/mod.rs:74）已存在且恰好覆盖所需 execute/cancel。重试预算、取消传播、超时、Success-但验证失败转重试这些最复杂路径无法 mock 单测。
- 方案：字段改 Option<Arc<dyn BridgeApi>>，LoginOrchestrator 构造处一行转换；mock 脚本化 Outcome 序列。
- 收益：seam 投入缺口最大的一块。工作量 M。

### A-3. 收敛两份虚拟网卡特征表
- 痛点：detect.rs:259-268（7 条）与 interfaces.rs:5-24（10 条）内容不同且在同一条过滤链先后生效，同一接口可能一处放行另一处拦截；均不识别 OpenVPN TAP/WireGuard/Clash TUN（对认证工具是真实误判源）。
- 方案：detect.rs 删 is_virtual_interface 改调 interfaces::is_excluded；差异特征（npcap）人工裁决并入单表；顺带补 tap/wireguard/clash/tun 模式。
- 工作量 S，有 detect_tests.rs 保护。

### A-4. 孤儿清理去 PowerShell 化 + 降频
- 痛点：bridge/mod.rs:859/1083 每次 spawn 与 Worker 退出都跑 powershell Get-CimInstance（冷启动 1-3s）；空闲回收后首个浏览器请求平白多等秒级。
- 方案：Windows 改 Toolhelp32 快照（windows_sys 已是依赖）；清理降频为生命周期首次 spawn + 异常退出时才执行。
- 收益：空闲后首请求快 1-3s（可测量）。工作量 S-M。

### A-5. system.rs(1111 行) 按域拆分 + 修复 container 旁路
- 痛点：混杂 7 个路由域；L872 task_writing_guide 直接触达 state.container 违背文件头 M1 约定，迁移漏网。
- 方案：拆出 routes/background.rs 与 routes/uninstall.rs；task_writing_guide 改走 State<Arc<dyn ConfigApi>>。
- 收益：container 旁路关闭后全域可注入测试。工作量 M。

### A-6. 原子写盘统一到 utils::io
- 痛点：updater/apply.rs:56-71 write_pending 手写 tmp+rename 无 fsync（断电半写 pending.json）；uv.rs:176-184 跨卷 rename→copy 第二份手写模板。config/scheduler/tasks 已正确复用 utils 版。

### A-7. tasks/executor.rs 补纯函数单测
